# مختبر الابتكار المستلهم من GitHub

حوّل مستودعات GitHub إلى **مصادر إلهام هندسية** لا إلى قوالب للنسخ. الهدف هو اقتراح أفكار أصلية قابلة للتجربة، ثم انتظار توجيه المستخدم قبل تنزيل مستودعات إضافية أو بناء نموذج أولي كامل.

## المبادئ الحاكمة

- ابتكر من **تقاطع مشروعين أو أكثر أو نمط تقني واضح**، ولا تكرر مستودعًا واحدًا كأنه ابتكار.
- ميّز دائمًا بين: ما هو موجود في المصدر، وما استنتجه التحليل، وما هو اقتراح جديد.
- افحص الترخيص، النشاط، التبعيات، الأمن، والملكية قبل اقتراح إعادة الاستخدام.
- لا تدّعِ أن الفكرة جديدة عالميًا؛ استخدم عبارات مثل «فجوة محتملة» و«تركيب ابتكاري مقترح».
- لا تنزّل أو تغيّر أو تنشر كودًا خارجيًا إلا عندما يطلب المستخدم ذلك بوضوح. التنزيل للتحليل فقط لا يعني صلاحية الاستخدام التجاري.
- للقرارات عالية المخاطر (الصحة، المال، الأمن، التوظيف، الحقوق): أضف مراجعة بشرية ومسار فشل آمن، ولا تقدّم النموذج الأولي كمنتج جاهز.
- احترم الأسرار والبيانات الشخصية: لا تضع مفاتيح API أو بيانات حساسة في الملفات أو الأمثلة.

## سير العمل

### 1. تثبيت الهدف

استخرج من طلب المستخدم:

- المجال أو المشكلة.
- المستخدم المستهدف.
- القيد الأهم: التكلفة، الزمن، الخصوصية، الأداء، أو سهولة التنفيذ.
- مستوى الناتج المطلوب: فكرة فقط، دراسة، نموذج أولي، أو كود.
- أي لغة أو منصة مفضلة.

إذا كان الطلب عامًا جدًا، اقترح ثلاث مسارات قصيرة مختلفة بدل طرح سلسلة طويلة من الأسئلة.

### 2. البحث في GitHub

استخدم GitHub CLI أو أدوات البحث المتاحة. ابحث بعبارات متعددة حول **المشكلة والسلوك والتقنية**، لا باسم فكرة واحدة فقط. اجمع عادةً 3–6 مستودعات مستقلة، مع تفضيل المشاريع التي لديها README واضح، أمثلة، ترخيص صريح، ونشاط حديث.

لكل مستودع، سجّل:

| الحقل | المطلوب |
|---|---|
| الرابط والمالك | الرابط الكامل واسم المالك |
| الوظيفة | ماذا يفعل فعليًا |
| التقنية القابلة لإعادة الاستخدام | مكتبة، خوارزمية، واجهة، نمط، أو بيانات تجريبية |
| الدليل | README، مثال، اختبار، أو ملف محدد |
| النشاط | آخر تحديث، الإصدارات، وحالة الصيانة |
| الترخيص | نوعه، وما إذا كانت القيود واضحة |
| المخاطر | تبعيات، أمن، بيانات، أداء، أو غموض قانوني |

عند تحليل مستودع محلي، اقرأ README وملف الترخيص والملفات ذات الصلة فقط، واذكر مسار الملفات التي استندت إليها.

### 3. استخراج الأنماط

أنشئ جدولًا يفصل بين:

- **المكوّنات:** ما يمكن استخدامه كما هو.
- **الأنماط:** طريقة تنظيم المكوّنات أو إدارة الحالة أو التحقق.
- **القيود:** ما لا يحله المصدر.
- **الفرصة:** فجوة يمكن أن تعالجها فكرة جديدة.

لا تعتبر كثرة النجوم دليل جودة كافيًا. افحص قابلية التشغيل، الاختبارات، التوثيق، والمجتمع.

### 4. تركيب الفكرة

كوّن الابتكار من الصيغة التالية:

> مشكلة واضحة + مستخدم محدد + تركيب تقني مستلهم من عدة مصادر + اختلاف جوهري قابل للاختبار + نموذج أولي صغير.

اشرح بوضوح ما الجديد. أمثلة الاختلاف الجوهري:

- دمج نمطين لم يُستخدما معًا في المصدر.
- نقل تقنية إلى مجال مختلف مع معالجة قيوده.
- إضافة طبقة أمان أو خصوصية أو تفسير.
- جعل الحل يعمل محليًا أو بتكلفة أقل.
- تحويل مكتبة إلى منتج أو سير عمل قابل للقياس.

### 5. تقييم قابلية التنفيذ

قيّم الفكرة من 1 إلى 5 في:

- قيمة المشكلة.
- الجِدّة التركيبية.
- سهولة بناء نموذج أولي.
- توفر المكوّنات.
- المخاطر القانونية/الأمنية.
- قابلية التوسع.

اذكر الافتراضات التي قد تغيّر التقييم. لا تستخدم درجة واحدة غامضة.

### 6. تقديم الفكرة للمستخدم

إذا طلب المستخدم «فكرة» فقط، لا تبدأ بالتنفيذ. قدّم فكرة واحدة قوية أو ثلاث أفكار موجزة، ثم اطلب توجيهًا محددًا مثل: «حلّل الفكرة الثانية»، «نزّل المصادر»، أو «ابنِ نموذجًا أوليًا».

استخدم هذا القالب:

**المجال:** ...  
**الفكرة في سطر واحد:** ...

...

## الخطوة التالية المقترحة
اطلب من المستخدم اختيار واحد: **بحث أعمق، تنزيل المصادر، تصميم معماري، أو بناء نموذج أولي**.

### 7. عند طلب التنزيل أو البناء

قبل التنفيذ:

1. اعرض قائمة المستودعات والهدف من كل تنزيل.
2. افحص الترخيص والتبعيات والثغرات المعروفة عندما تتوفر أدوات لذلك.
3. استخدم مجلد عمل منفصل، ولا تعدّل المصدر الأصلي مباشرة.
4. ثبّت الإصدارات أو commit محددًا عند الإمكان.
5. شغّل الاختبارات أو مثالًا صغيرًا قبل الدمج.
6. وثّق ما تم نسخه، وما تم تغييره، وأي تعارض ترخيص.
7. لا تنفّذ نشرًا عامًا أو تغييرًا خارجيًا دون طلب صريح.

## نمط خاص: الابتكار في أتمتة الذكاء الاصطناعي

عند تصميم n8n أو سير عمل متعدد النماذج، استفد من أنماط المستودع المرجعي `mylawmhmd2-cmd/Dcwd`، مثل:

- **Majority Gate:** توافق عدة مخرجات قبل القبول.
- **Priority Encoder / Arbiter:** تمرير الحالة الأعلى خطورة أولًا.
- **Hysteresis:** منع تقلب القرار قرب العتبة.
- **Finite State Machine:** ضبط دورة الحياة ومنع الانتقالات غير المسموحة.
- **Feedback Loop:** إعادة الجزء الفاشل مع حد واضح للمحاولات.
- **Safety Interlock:** إيقاف التنفيذ عند إخفاق فحص حرج.

لا تنسخ أمثلة المستودع حرفيًا. حلّل سلوك المشكلة أولًا، ثم صمّم تركيبًا جديدًا. وثّق المدخلات والمخرجات ومالك الحالة وإعادة المحاولة والمهلة والتكرار والتسليم خارج الترتيب.

إذا كان سير العمل يتخذ قرارًا مؤثرًا على أشخاص أو فرص، أضف تدقيق إنصاف، اختبارًا مقابلًا، مسار `HUMAN_REVIEW`، وسجل أدلة قبل بوابة القرار. لا تعتبر تصويت الأغلبية وحده ضمانًا للإنصاف.

## قائمة فحص قبل التسليم

- [ ] استندت الفكرة إلى مصادر فعلية وروابط قابلة للتحقق.
- [ ] فُصل الموجود عن الاستنتاج عن الابتكار المقترح.
- [ ] أُدرج الترخيص والمخاطر لكل مصدر.
- [ ] وُضحت الجدة دون ادعاء أولوية عالمية.
- [ ] يوجد نموذج أولي صغير واختبار نجاح قابل للقياس.
- [ ] ذُكرت القيود والافتراضات.
- [ ] لم تُكشف أسرار ولم تُنسخ بيانات شخصية.
- [ ] أضيفت مراجعة بشرية ومسار فشل آمن عند ارتفاع المخاطر.
- [ ] لم يبدأ تنزيل أو تعديل أو نشر غير مطلوب.

## النشر إلى مستودع المستخدم

بعد اكتمال تطوير المهارة وفحصها بنجاح، وعندما تكون صلاحية GitHub متاحة:

1. انسخ المهارة إلى مجلد واضح داخل مستودع المستخدم، مثل `skills/github-innovation-lab/`، مع ملف `SKILL.md` والمراجع اللازمة فقط.
2. لا تستبدل ملفًا موجودًا دون فحص الفرق أولًا.
3. أنشئ commit وصفيًا، ثم ادفعه إلى الفرع الافتراضي للمستودع الذي حدده المستخدم.
4. تحقق من رابط الملف على GitHub، وسجّل commit والرابط في النتيجة.
5. إذا فشل الدفع أو طلب GitHub مراجعة، توقف واذكر السبب بدل الادعاء بالنجاح.

يُفضّل أن يحتوي المستودع على README أو فهرس قصير يشرح مكان المهارة وطريقة استخدامها، من دون تضمين أسرار أو ملفات بيئة محلية.

## اكتشاف أخطاء مشاريع n8n والتواصل مع أصحابها

عندما يطلب المستخدم العثور على مشاريع n8n ذات «مسارات خاطئة»، فسّر ذلك على أنه بحث عن أخطاء قابلة للتحقق في مسار سير العمل، مثل:

- عقدة تشير إلى عقدة غير موجودة أو اسم قديم.
- اتصال `main` غير صالح أو مخرج لا يطابق نوع العقدة.
- تعبير يستعمل مسار JSON غير موجود في البيانات الفعلية.
- عقدة أو credential أو متغير بيئة مذكور في التوثيق لكنه مفقود من المثال.
- حلقة إعادة محاولة بلا حد أو مسار فشل لا ينتهي إلى حالة آمنة.
- اختلاف واضح بين نسخة n8n المعلنة وبنية workflow المستخدمة.

لا تعتبر اختلاف أسلوب أو نقصًا غير مثبت «خطأ». افحص README، ملفات workflow JSON، الأمثلة، والـ issue tracker عند الحاجة، وسجّل الدليل الدقيق: اسم الملف، العقدة، المسار، أو السطر.

### معيار اختيار المشاريع

- اختر مشاريع n8n عامة ومشروعة وقابلة للفحص.
- ابدأ بعينة صغيرة (عادة 3–5 مشاريع) ولا ترسل رسائل جماعية أو مكررة.
- لا تفحص مستودعات خاصة أو بيانات شخصية، ولا تحاول تشغيل workflow قد يرسل رسائل أو يعدّل بيانات خارجية.
- لا تفترض أن صاحب المستودع هو «صاحب مهارة»؛ خاطبه بصفته مالك المشروع أو المساهم، وبأدب.

### قبل إرسال رسالة

لكل مشروع مرشح، أنشئ بطاقة:

| الحقل | المحتوى |
|---|---|
| المشروع | الرابط والمالك |
| الخطأ المحتمل | وصف محدد وقابل لإعادة الإنتاج |
| الدليل | الملف/العقدة/المسار/السطر |
| الأثر | ما الذي قد يتعطل ولماذا |
| الإصلاح المقترح | خطوة قصيرة قابلة للاختبار |
| الثقة | عالية، متوسطة، أو منخفضة |
| قناة التواصل | Issue أو Discussion أو PR، إن كانت متاحة |

لا ترسل أي رسالة إذا كانت الثقة منخفضة أو كان الدليل مجرد تخمين. ابدأ بـ Issue واحدة محترمة في المستودع، أو Discussion إن كان ذلك هو المكان المناسب. لا ترسل رسائل خاصة أو طلبات ترويجية إذا لم يوفر صاحب المشروع قناة عامة واضحة.

### قالب الرسالة

اكتب الرسالة بلغة المشروع، وكن شفافًا بأنك تستخدم مهارة لتحليل مشاريع GitHub. لا تصف المهارة كجهة رسمية ولا تطلب من المالك تبنيها. استخدم هذا القالب:

```markdown
## ملاحظة قابلة لإعادة الإنتاج حول مسار n8n

مرحبًا، أثناء مراجعة مشروعكم وجدت احتمالًا في `[الملف/العقدة]`:

- **المسار/الاتصال المتأثر:** `...`
- **المشكلة:** ...
- **الأثر المتوقع:** ...
- **طريقة التحقق:** ...

أقترح تجربة: ...

قد أكون مخطئًا إذا كانت هذه القيم تُضاف في بيئة تشغيل مختلفة؛ لذلك أرجو التحقق من النسخة `...`.

للمهتمين بالمنهج الذي استخدمته في التحليل، هذه مهارتي المفتوحة:
[GitHub Innovation Lab](https://github.com/OWNER/REPO/tree/main/skills/github-innovation-lab)

شكرًا على المشروع، ويسعدني تعديل الملاحظة إذا زودتموني بسياق إضافي.
```

عدّل الرابط إلى الرابط الفعلي بعد النشر. لا تضع رابط المهارة في عنوان الرسالة، ولا تستخدم لغة تسويقية أو ادعاء أن الإصلاح مؤكد.

### سجل التواصل

بعد إرسال كل رسالة، سجّل الرابط العام للـ Issue أو Discussion وتاريخ الإرسال في تقرير محلي. لا تعاود مراسلة المشروع نفسه تلقائيًا إلا إذا طلب المستخدم ذلك أو ظهرت معلومات جديدة جوهرية. لا تنشئ حسابات أو تتجاوز حدود GitHub أو CAPTCHA، ولا تنشر تعليقات آلية على عدد كبير من المشاريع.

## حدود الموافقة

- رفع المهارة إلى مستودع المستخدم بعد طلبه الصريح مسموح ضمن نطاق المهمة.
- فتح Issue أو Discussion محددة وودية مع دليل واضح هو تواصل خارجي منخفض الأثر ويمكن تنفيذه بناءً على طلب المستخدم.
- لا تنشر تغييرات كود في مشروع شخص آخر، ولا تنشئ PR، ولا تراسل بريدًا أو حسابًا خاصًا، ولا تنفّذ أي إجراء واسع أو غير قابل للعكس دون طلب صريح منفصل.
